# PatchCore의 Jetson Xavier NX TensorRT 이식 보고서

상태: JetPack 5.1.4(TensorRT 8.5.2)에서 정확도 15개 카테고리, 속도, 전력, 열 안정성을 측정함. DLA 엔진의 정확도와 GPU와 DLA를 함께 쓰는 파이프라인의 정확도는 미측정임. JetPack 4.6.1(TensorRT 8.2.1)의 값은 비교용으로 별도 표기함.

## 요약

- MVTec AD 15개 카테고리에서 TensorRT 혼합 정밀도 엔진의 정확도가 fp32 기준과 같음. 평균 image AUROC 0.9802(기준 0.9816), pixel AUROC 0.9784(0.9780), AUPRO 0.9218(0.9215)임.
- RK3588 NPU는 모든 층을 INT8로 양자화해야 했으나 Jetson에서는 민감한 앞쪽 층(stem과 layer1.0)만 fp16으로 남길 수 있음. 최고 성능 모드에서 이 엔진은 fp16보다 63% 빠름(189 FPS 대 116 FPS).
- 같은 엔진의 장당 에너지는 80 mJ이고 fp16은 130 mJ임.
- DLA 코어 2개와 GPU를 동시에 쓰면 GPU 단독보다 처리량이 37%(fp16) 또는 41%(int8) 늘고 장당 에너지는 오히려 낮음. DLA int8 엔진은 보정 전이라 정확도를 확인하지 못함.
- 10분 연속 실행에서 GPU 클럭이 1109 MHz로 유지되었고 온도는 69.5°C에서 멈춤. 속도 저하가 없었음.
- 후처리 전체와 원본 해상도 리사이즈를 ONNX 그래프 안으로 옮겨도 정확도가 유지됨(bottle 기준). TensorRT에서의 속도 효과는 미측정임.
- anomalib 기본 설정 baseline은 TensorRT fp16에서 64 ms로 RK3588의 977 ms보다 빠르고 정확도는 같음.
- screw에서 coreset을 1%에서 5%로 올리면 AUPRO가 0.9127에서 0.9409가 됨. 1% coreset은 NPU에 맞춘 선택이었음.

## 모델과 파이프라인

- backbone: WideResNet50의 layer2와 layer3, 1536 채널.
- 차원 축소: 고정 random projection으로 384 채널.
- memory bank: coreset 1%(bottle 기준 2140행)이며 k-center greedy로 선택함.
- kNN: 1x1 Conv로 `m = max(2*x*b - ||b||^2)`를 계산하고 프로젝션을 업샘플 앞으로 옮긴 융합 ONNX 하나로 만듦.
- 점수: `sqrt(||xproj||^2 - m)`이며 image score는 최댓값 또는 상위 10개 patch 평균임.
- 입력: 원본 RGB를 NHWC float32 0~255로 받고 정규화와 NCHW 변환을 그래프 안에서 처리함.

RK3588에서 쓴 변환 중 `rewrite_max_tree`, `rewrite_raw_out`, 카테고리별 분할 단계 탐색, mean과 std를 변환 설정에 넣는 방식, `mmse` 보정은 NPU 전용이라 가져오지 않음.

- 층 지정을 이름 기준으로 해도 번호 기준과 같은 엔진이 만들어짐. TensorRT 버전이 바뀌어도 이름 기준이 안전함.

## baseline

anomalib 기본 설정(coreset 10%, 1536 채널)을 TensorRT 8.2.1에서 실행함.

| 구성 | image AUROC | pixel AUROC | AUPRO | 지연 |
|:---:|:---:|:---:|:---:|:---:|
| onnxruntime fp32 | 1.0000 | 0.9853 | 0.9437 | 해당 없음 |
| TensorRT fp16, batch 1 | 1.0000 | 0.9854 | 0.9447 | 64.3 ms |
| TensorRT fp16, batch 2 | 1.0000 | 0.9854 | 0.9448 | 60.4 ms/장 |
| RK3588 RKNN fp16 | 1.0000 | 0.9854 | 값 없음 | 977 ms |

- TensorRT가 읽도록 ONNX를 네 곳 고쳤음: opset 17 TorchScript 내보내기, 후처리의 빈 상수 폴딩, Flatten을 Reshape로 교체, `TopK(largest=0)`을 부호 반전 후 `TopK(largest=1)`로 교체함.
- 마지막 수정 전에는 TensorRT 8.2.1이 `largest=0`을 무시해서 image AUROC가 0.63이었음.
- 이 baseline은 JetPack 4.6.1에서만 측정했고 5.1.4에서는 아직 다시 재지 않음.

## 속도와 전력

JetPack 5.1.4, TensorRT 8.5.2, bottle, 입력 256, batch 1임. 전력은 tegrastats의 VDD_IN(모듈 전체)이며 시간 평균임.

| 엔진 | 모드 | FPS | GPU 연산 | 평균 전력 | 장당 에너지 |
|:---:|:---:|:---:|:---:|:---:|:---:|
| fp16 | 10W 기본 | 62.3 | 16.0 ms | 10.1 W | 162 mJ |
| 혼합 정밀도 | 10W 기본 | 99.6 | 9.8 ms | 9.7 W | 97 mJ |
| int8 minmax | 10W 기본 | 113.6 | 8.6 ms | 9.6 W | 84 mJ |
| fp16 | 최고 성능 | 116.2 | 8.6 ms | 15.1 W | 130 mJ |
| 혼합 정밀도 | 최고 성능 | 189.1 | 5.2 ms | 15.1 W | 80 mJ |
| int8 minmax | 최고 성능 | 217.4 | 4.5 ms | 15.3 W | 70 mJ |
| 혼합 정밀도, 스트림 2개 | 최고 성능 | 219.2 | 8.9 ms | 17.6 W | 80 mJ |
| int8 minmax, 스트림 2개 | 최고 성능 | 257.8 | 7.6 ms | 해당 없음 | 해당 없음 |

- CUDA Graph는 2%, 데이터 전송 제외는 1% 안팎의 차이만 냄. 모델이 GPU 연산에 묶여 있음.
- 스트림을 늘리면 GPU에 여유가 있을 때만 효과가 있고 프레임당 지연은 늘어남.
- int8 minmax의 정확도는 혼합 정밀도보다 낮아(bottle AUPRO 0.9341 대 0.9430) 정확도를 지켜야 하는 용도에는 혼합 정밀도가 맞음.
- JetPack 4.6.1에서 같은 조건의 값은 최고 성능 모드 혼합 182 FPS, fp16 116 FPS였음.
- 이 수치는 GPU 연산 시간 중심이며 전처리와 후처리를 포함한 끝단 처리량이 아님.

## DLA와 GPU의 동시 실행

DLA 엔진은 입력 앞단의 Transpose와 정규화, head의 ReduceMax는 GPU로 되돌아가는 구성으로 빌드함(`allowGPUFallback`). int8 DLA 엔진은 보정 없이 만든 것이라 속도만 의미가 있음.

| 구성 | FPS | 평균 전력 | 장당 에너지 |
|:---:|:---:|:---:|:---:|
| DLA 코어 하나, fp16 | 49.3 | 7.6~7.9 W | 약 155 mJ |
| DLA 코어 하나, int8(보정 전) | 87.6 | 6.6 W | 약 75 mJ |
| DLA 2개와 GPU(fp16)를 동시에 | 159.0 | 18.5 W | 116 mJ |
| DLA 2개(int8, 보정 전)와 GPU(혼합)를 동시에 | 266.3 | 16.9 W | 63 mJ |

- GPU 단독 대비 처리량이 fp16 조합은 37%(116에서 159), int8 조합은 41%(189에서 266) 늘어남. DLA와 메모리 대역폭을 나눠 쓰므로 GPU 쪽 엔진은 단독일 때보다 느려짐.
- DLA를 쓰면 GPU 사용률이 4~7%에 그쳐서 같은 시간에 GPU를 다른 작업에 쓸 수 있음.
- DLA int8 엔진의 정확도는 미측정이며, 266 FPS 조합의 의미는 이 정확도에 달려 있음.

## 열 안정성

혼합 정밀도 엔진을 스트림 2개로 최고 성능 모드에서 10분 동안 연속 실행함.

- 평균 217.2 FPS이고 GPU 클럭은 10분 내내 1109 MHz로 유지됨.
- GPU 온도는 64.0°C에서 시작해 69.5°C에서 멈춤. 전력은 약 19 W임.
- 팬은 커널이 정한 상한(PWM 160, 약 3800 rpm)으로 돌았고 온도가 더 오르지 않았음.

## 그래프 수준 변환

PC에서 onnxruntime으로 검증한 결과이며 TensorRT 실행과 속도 측정은 아직 하지 않음. bottle과 screw의 결과임.

| 변환 | bottle pixel / AUPRO | screw pixel / AUPRO |
|:---:|:---:|:---:|
| 호스트 후처리(기준) | 0.9848 / 0.9430 | 0.9801 / 0.9127 |
| 후처리(sqrt, 상위 10개 평균, 업샘플, 가우시안)를 그래프 안으로 | 0.9848 / 0.9430 | 0.9801 / 0.9127 |
| 블러를 저해상도에서 하고 nearest로 확대 | 0.9842 / 0.9417 | 0.9750 / 0.8985 |
| 블러를 저해상도에서 하고 bilinear로 확대 | 0.9848 / 0.9425 | 0.9801 / 0.9120 |
| 원본 해상도 입력, 단순 bilinear 리사이즈 | 0.9830 / 0.9396 | 0.9862 / 0.9379 |
| 원본 해상도 입력, 행렬곱으로 Pillow 안티앨리어싱 재현 | 0.9849 / 0.9432 | 0.9792 / 0.9088 |

- 후처리를 그래프 안으로 옮기면 점수 차이가 2e-5, 맵 차이가 3e-4 이하이며 모든 지표가 같음.
- 세 부분(stem부터 layer2, layer3, head)으로 나눈 그래프를 이어 붙이면 원래 출력과 차이가 0임. 분할 지점의 특징 크기는 layer2 출력 [1,512,32,32]와 layer3 출력 [1,1024,16,16]임.
- 리사이즈 방식은 screw에서 결과를 크게 바꿈. 다만 memory bank는 Pillow 방식으로 만든 학습 이미지에서 나온 것이라 학습과 추론의 방식이 다른 상태임. 같은 방식으로 bank를 다시 만든 비교가 필요함.

## 보드 준비에서 확인한 사항

- 처음 JetPack 5.x를 쓰는 Xavier NX 개발자 키트는 QSPI 펌웨어를 먼저 올려야 함. 4.x 시스템에서 `flash_erase`와 `flashcp`로 쓰고 전체를 다시 읽어 해시를 비교함. 기존 QSPI는 먼저 백업함.
- 5.1.4 이미지로 처음 부팅하면 부트로더가 35.1이고 OS가 35.6이어서 CPU와 GPU 온도 존이 만들어지지 않음. 한 번 재부팅하면 부트로더가 35.6으로 갱신되고 온도 존 6개가 모두 나타남. 약 1.5분 걸림.
- 4.6.1에서는 팬 회전수 센서를 쓸 수 없어 `rpm_measured`가 항상 0이었으나 5.1.4에서는 읽을 수 있음. 팬이 정상 동작함.
- 4.6.1에서 `target_pwm`에 0을 쓰면 자동 온도 제어가 꺼져 67°C에서도 팬이 멈춤. `board/fan_daemon.sh`가 온도 구간별로 PWM을 쓰며, 5.1.4에서는 systemd 서비스로 등록함.
- 5.1.4의 커널은 온도에 따라 팬 PWM의 상한을 정하며 상한을 넘는 값을 쓰면 상한으로 잘림(255를 써도 130 유지). 성능 측정 중에도 팬을 최대로 고정할 수 없음.
- Windows 관리자 권한 콘솔(conhost)에서는 Shift+Enter를 구분하지 못해 Windows Terminal로 실행해야 함.
