# Jetson Xavier NX LLM 기본 모델 측정

## 환경
- 보드: Jetson Xavier NX dev kit, JetPack 5.1.4 (L4T R35.6.0), 메모리 6.8 GB를 CPU와 GPU가 공유함
- 빌드: llama.cpp v0.8.0 (커밋 8642541b, MIT), CUDA 11.4, sm_72, Release, CMake 3.31.12 (Kitware 공식 릴리스, SHA-256 확인)
- 모델: Qwen2.5-1.5B-Instruct Q4_K_M GGUF (Apache 2.0), 1,117,320,736 B, sha256 6a1a2eb6d156...e9407e
- 측정 도구: llama-bench, 3회 반복(최대 모드 GPU는 5회), 전력은 tegrastats VDD_IN
- 최대 모드는 nvpmodel 20W 6코어와 jetson_clocks를 켠 상태임. 일반 모드는 10W 데스크톱 모드임

## 결과 (tok/s)

| 구성 | 모드 | pp128 | pp512 | tg128 |
|---|---|---|---|---|
| GPU 전 레이어 | 10W | 257.6 | 459.1 | 18.3 |
| GPU 전 레이어 + flash attention | 10W | 255.7 | 459.4 | 18.3 |
| CPU 4스레드 (ngl 0) | 10W | 175.3 | 측정 안 함 | 5.1 (tg32) |
| GPU 전 레이어 | 최대 | 479.9 | 757.7 | 34.2 |
| CPU 4스레드 (ngl 0) | 최대 | 247.4 | 측정 안 함 | 4.8 (tg64) |

## 전력과 온도 (최대 모드, VDD_IN)
- GPU 실행 평균 12.9 W (pp512 구간 포함), 최고 17.1 W임
- CPU 실행 평균 7.2 W, 최고 12.1 W임
- GPU 최고 온도 50 °C이고 팬은 동작 중이라 열 제한은 없었음

## 해석
- 디코딩은 최대 모드에서 10W 모드 대비 1.87배 빨라짐 (18.3 에서 34.2). 프리필(pp512)은 1.65배임
- 디코딩은 GPU가 CPU의 약 7배임 (34.2 대 4.8). CPU는 모드를 올려도 거의 변하지 않음 [Reasoned: CPU 디코딩은 4스레드 연산과 메모리 대역폭이 한계]
- flash attention은 이 모델과 이 길이에서 차이가 없음 (오차 범위 안)
- 메모리는 모델 적재 후 약 0.85 GB 증가함. 6.8 GB 중 가용 약 4.7 GB가 남음

## 주의
- CPU 프리필 수치(175, 247)는 `-ngl 0`이어도 CUDA 백엔드가 큰 배치의 일부 연산을 GPU로 넘겼을 가능성이 있어 순수 CPU 값으로 쓰지 않음. CPU 디코딩 수치는 영향이 작을 것으로 봄 [Unknown: 미확인]
- 10W 모드 측정은 팬 단계가 낮은 상태에서 돌았음. 온도 로그를 남기지 않아 열 영향은 배제하지 못함

## 재현
- `get_model.sh` 모델 내려받기, `build_llama.sh` 구성과 빌드, `bench10w.sh` 일반 모드 벤치, `run_llm_max.sh` 최대 모드 벤치 (root, 종료 시 일반 모드 자동 복귀)

## PatchCore 파이프라인과 동시 실행 (최대 모드)
- 방법: llama-bench(디코딩 tg128, 30회)를 먼저 시작하고 15초 뒤에 PatchCore 파이프라인(30초 측정, 5초 워밍업, resize 스레드 2, queue depth 4)을 시작함
- 같은 보드, 같은 세션의 단독 측정값과 비교함 (LLM 34.2 tok/s, PatchCore는 이전 측정값)

| 동시 실행 구성 | LLM 디코딩 단독 | LLM 디코딩 동시 | PatchCore 단독 | PatchCore 동시 | 보드 평균 전력 |
|---|---|---|---|---|---|
| 2 DLA + CPU 후처리 (PIPE_P4_dla0_dla1_pt2) | 34.2 | 약 23.5 (-31%) | 128.6 FPS | 97.8 FPS (-24%) | 16.4 W |
| GPU 단일 (PIPE_P1_gpu) | 34.2 | 약 13.9 (-59%) | 152.6 FPS | 50.2 FPS (-67%) | 15.9 W |

- 동시 실행 구간이 끝나면 LLM 속도는 34 tok/s로 바로 돌아옴. 지속적인 열 제한이나 성능 저하는 없었음
- DLA 구성은 GPU를 공유하지 않아 두 작업 모두 70% 이상을 유지함. GPU 구성은 같은 GPU를 시분할해서 둘 다 크게 떨어짐
- DLA 구성의 LLM 저하 31%는 GPU 경합이 아니라 CPU 스레드와 메모리 대역폭 공유 때문으로 봄 [Reasoned: 확인 실험은 안 함]
- 결론: 두 작업을 한 보드에서 같이 운용하려면 PatchCore를 2 DLA로 옮기는 것이 낫음. GPU 배치는 LLM과 함께 쓰기에 부적합함
- 한계: 각 케이스 1회 측정이고 LLM 구간 경계는 반복 단위(약 4초) 해상도임

## vLLM 0.2.2 (JetPack 5, 단일 모델)
- 결론: 동작함. 단, 이 보드에서는 오래된 vLLM(0.2.2)을 소스 빌드하고 호환용 shim 두 개를 넣어야 했음. 최신 vLLM은 시도하지 않음
- 구성: Python 3.8 virtualenv, NVIDIA JetPack 5용 PyTorch 2.1.0a0 (CUDA 11.4), vLLM 0.2.2 소스 빌드 (`MAX_JOBS=1`, 약 1시간)
- 모델: TinyLlama-1.1B-Chat-v1.0 (Apache 2.0), fp16, 2.2 GB. vLLM 0.2.2가 Qwen2를 지원하지 않아 Qwen2.5-1.5B 대신 Llama 구조 모델을 사용함
- 설정: `gpu_memory_utilization=0.4`, `max_model_len=1024`, `swap_space=1`, 128 토큰 출력, greedy

막혔던 지점과 처리
| 문제 | 원인 | 처리 |
|---|---|---|
| xformers 설치 불가 | aarch64 휠이 없고 소스 빌드가 매우 무거움 | torch SDPA로 구현한 최소 호환 shim을 venv에 설치 (실제 xformers 아님) |
| `torch.distributed` 없음 | Jetson용 PyTorch 휠이 distributed 없이 빌드됨 | 월드 크기 1 전용 스텁을 실행 스크립트 앞에 추가 (vLLM 소스는 수정 안 함) |
| "no kernel image" | 기본 빌드가 sm_70 바이너리만 생성하고 PTX가 없어 sm_72에서 실행 불가 | 내려받은 소스의 `setup.py` 지원 목록에 7.2를 추가해 sm_72로 재빌드 |
| 프로세스 강제 종료(OOM) | 기본 CPU 스왑 4 GiB 고정 메모리와 GPU 몫이 6.8 GB 공유 메모리를 초과 | `swap_space=1`, GPU 사용률 0.4 |

결과 (디코딩 tok/s, 배치 크기별)
| 모드 | 배치 1 | 배치 4 | 배치 8 |
|---|---|---|---|
| 10W | 15.7 | 58.3 | 108.5 |
| 최대 | 22.7 | 87.8 | 151.4 |

- 배치를 늘리면 처리량이 거의 선형으로 늘어남 (최대 모드 배치 8은 배치 1의 6.7배). 디코딩이 메모리 대역폭 한계라서 가중치 읽기를 여러 요청이 나눠 쓰기 때문임 [Reasoned]
- 배치 1의 22.7 tok/s x 가중치 2.2 GB는 약 50 GB/s로, Xavier NX의 메모리 대역폭 상한(약 51 GB/s)에 가까움 [Reasoned: 계산값이며 대역폭 직접 측정은 안 함]
- 같은 모델이 아니라 llama.cpp 수치와 직접 비교하지 않음. 참고로 Q4 1.5B 모델은 llama.cpp가 최대 모드에서 34.2 tok/s였음
- 전력: 최대 모드 측정 전체 평균 7.5 W, 최고 15.6 W, GPU 최고 46 °C. 평균에는 모델 적재 구간이 섞여 있어 추론 중 전력으로 쓰지 않음
- 한계: vLLM 0.2.2는 2023년 말 버전이라 CUDA graph, continuous batching 최적화 등 최신 기능이 없음. TensorRT-LLM은 JetPack 6 이상만 지원해서 시도하지 않음
- 재현: `vllm_stage1.sh` 환경과 PyTorch, `vllm_stage2.sh` 소스 빌드, `vllm_stage3.sh` 의존성, `xformers_shim/`, `get_tinyllama.sh`, `vllm_stage4.sh` sm_72 재빌드, `vllm_smoke.py`, `run_vllm_max.sh`

## 모델 서빙 (llama-server, 단일 모델)
- 방향: vLLM을 억지로 쓰지 않고, 빌드해 둔 llama.cpp의 `llama-server`로 언어 모델 서빙을 측정함. vLLM 결과는 참고용으로만 둠
- 구성: Qwen2.5-1.5B-Instruct Q4_K_M, `-ngl 99 -c 4096 -np 4` (슬롯 4개, 슬롯당 컨텍스트 1024), OpenAI 호환 `/v1/chat/completions` 스트리밍, 127.0.0.1에서 보드 내부 클라이언트로 호출
- 부하: 프롬프트 1개(약 100단어 설명 요청), 출력 128 토큰 상한, greedy, 동시 접속 수마다 접속당 3회 요청, 워밍업 1회 제외
- 같은 모델에 대한 동시 요청만 측정했고 다른 모델 동시 실행은 하지 않음

결과
| 모드 | 동시 접속 | 총 처리량 (tok/s) | 요청당 디코딩 (tok/s) | 첫 토큰 지연 중앙값 (s) | 첫 토큰 지연 최대 (s) |
|---|---|---|---|---|---|
| 10W | 1 | 17.7 | 17.8 | 0.066 | 0.088 |
| 10W | 2 | 32.1 | 16.1 | 0.083 | 0.085 |
| 10W | 4 | 39.4 | 10.0 | 0.143 | 0.409 |
| 최대 | 1 | 32.1 | 32.3 | 0.048 | 0.050 |
| 최대 | 2 | 57.5 | 29.0 | 0.059 | 0.088 |
| 최대 | 4 | 73.5 | 18.5 | 0.090 | 0.120 |

- 최대 모드에서 동시 접속 4개일 때 총 처리량은 단독의 2.3배(73.5 대 32.1)이고, 접속당 속도는 18.5 tok/s로 단독의 57%임. 10W 모드는 2.2배, 접속당 56%임
- 첫 토큰 지연은 모든 구성에서 0.5초 미만이고, 짧은 프롬프트라서 체감상 즉시 응답함
- 접속 2개까지는 총 처리량이 거의 선형으로 늘고, 4개에서는 늘어나는 폭이 줄어듦 (GPU 연산이 한계에 가까워지는 것으로 보임 [Reasoned])
- 서버 상주 메모리: 보드 사용 메모리 약 2.8 GB (모델 적재 후), 가용 약 3.9 GB가 남음
- 전력: 최대 모드 측정 전체 평균 15.5 W, 최고 17.0 W, GPU 최고 49.5 °C임. 동시 접속 수가 다른 구간이 섞인 평균임
- 한계: 프롬프트 길이를 1종류로만 측정했고, 긴 컨텍스트와 긴 프롬프트의 프리필 지연은 측정하지 않음
- 재현: `serve_bench.sh` (서버 기동, 부하, 종료), `serve_client.py` (스트리밍 부하 클라이언트), `run_serve_max.sh` (root, 최대 모드)
